# CC FLOW 性能与通知布局排查（2026-09-30）

## 范围与证据

检查了通知入口到 SessionStore / SessionMonitor / NotchViewModel / NotchView / AppKit 窗口的更新链路，以及音乐进度、GIF 缩略图、系统监控与后台维护。没有修改界面配色、功能排序或用户通知策略。

对当时运行的 Debug 应用（PID 13177）进行了 5 秒、5ms 间隔的 `sample` 采样。进程快照 CPU 为 38.2%，RSS 约 195MiB；采样报告 physical footprint 为 456.6M。这是用户当前场景的快照，不是受控空闲基准，也不能据此判断内存泄漏。

采样文件：`/tmp/ccflow-performance-before.txt`。主线程调用栈包含 GIF 图像解码、SwiftUI/AppKit 布局，以及 `SystemMonitorService.refresh → diskCapacity → URL.resourceValues`。没有采到足以证明通知处理是全部 CPU 消耗来源的证据。

## 已复现并修复

| 问题 | 证据 | 修复 |
| --- | --- | --- |
| 重复通知重新发布展开状态并清空高度 | 设置高度 320 后连续调用通知展开 10 次，旧实现退回 170，并各发布 10 次 status / openReason | 相同展开状态与原因不重复赋值；只有切换展示上下文时清空测量高度 |
| 顶部栏提交半完成的布局 | 原点与大小依次变化时，布局完成前顶部窗口已发生变化 | 合并帧同步请求，在完整布局或下一轮主循环提交几何位置 |
| GIF 随父视图更新重新加载 | 连续 100 次更新相同 URL，旧实现更换 NSImage 实例；切换到无效文件还保留旧图 | 原生缩略图按 URL 复用图片与播放时间线，源变化时才读取；失效源清空旧图 |
| 音乐进度扩大刷新范围 | NowPlayingProvider 每 0.2 秒更新 elapsed，NotchView 订阅整个对象，但根视图只需播放/暂停决定自动功能选择 | 根视图只订阅去重后的 isPlaying；音乐子视图继续处理进度 |
| 完成提示弹簧影响展开面板 | isBouncing 的动画修饰器作用于整棵灵动岛树 | 仅紧凑态启用完成提示弹簧，已展开状态不安排该动画 |
| 磁盘容量查询阻塞 UI | 实际采样捕获到主线程同步卷容量查询 | 显式 @concurrent 后台查询，单任务运行；停止订阅时取消并丢弃旧结果 |

GIF 文件由 Giflow 导出为独立 URL；本次复用不处理外部程序原地覆盖同一个文件的情况。正常 GIF 动画解码仍有成本，修复消除的是无关状态更新造成的重新加载，不代表所有 GIF CPU 开销都已消失。

## 检查后保留的机制

- SessionStore 对发布快照去重；SessionMonitor 对全量会话、可见会话、待处理会话分别去重。
- 文件同步已有 100ms 防抖。
- EnergyGovernor 的会话维护间隔为活跃 60 秒、空闲可见 5 分钟、后台 10 分钟；休眠时暂停维护。没有为了降低 CPU 而减少通知正确性。
- 系统监控仍由视图消费者启动/停止，采样周期仍为 2 秒。
- WebView 保活属于既有音乐/网页行为，本次没有关闭或改变。
- 窗口最终仍为顶部菜单栏层、下方浮动层；没有恢复整个窗口长期占用菜单栏层。
